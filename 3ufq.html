Reviewer 3ufq · W1

How much work does dataset annotation require?

Reviewer’s original text · Critical Weakness 1
Though with LLM assisted, but the human labeling/annotation seems still non-trivial work for 100K rollouts. The authors should provide efficiency related report on data curation and annotation process, including token usage, human labor hours etc.

Response

Dataset construction combines GPT-assisted annotation with human verification. Human annotators identify event types and mark key time points based on visible state changes in the videos, without assigning precise framewise progress values. The annotation rate is approximately 260–330 trajectories per person-hour, or about 11–14 seconds per trajectory. We manually annotated all 40,857 raw RoboChallenge trajectories used in our paper. Manual annotation took approximately 140 person-hours. Human annotations are compared with GPT proposals. Disagreements are reviewed by a third party, and annotation quality is checked through spot checks. As an example, for the publicly released RoboChallenge data used in our paper, we used GPT-5.6 Sol (medium reasoning) to propose candidate event annotations. Generating candidate event annotations for these data consumed approximately 3.8 billion tokens, with an estimated API cost of US$15,000–19,000.

To illustrate the annotation procedure, we provide a continuous screen recording covering all 87 complete episodes from the paper’s Ethernet-insertion training run (Figure R8 below). One author familiar with the event definitions completed these annotations in 9 minutes 53 seconds of active work, including revisions, averaging approximately 6.8 seconds per trajectory, equivalent to about 530 trajectories per hour. The recording shows the complete process of identifying events, marking key time points, and making revisions.

We will release the Event2Reward dataset, including the final event annotations used for training. Researchers can use the same annotations to train reward models and reproduce the policy-learning experiments without making additional GPT calls or repeating human annotation.

Response · Reviewer 3ufq · Question 4

What about slower progress and behavior more likely to fail?

Reviewer’s original text
In table 4, authors classify the robot execution events into 4 categories, though a concise high-level abstract but this seems cannot work well on more detailed scenarios reward model should react, e.g. suboptimal execution - robot still progressing, but slower and more easy to make mistakes.

Response

Event2Reward predicts continuous progress, so differences finer than the four event types still appear in the reward. When a robot progresses more slowly, each step receives a smaller shaping reward γpt+1 − pt. The four event types describe changes in progress within execution segments and provide supervision based on these changes. For example, a stall annotation constrains progress within the segment to remain approximately equal to that of a reference state, while a regression annotation constrains states after a loss of progress to have lower progress. The model combines these relational constraints with progress labels from successful trajectories to learn continuous task progress values. The four event types thus provide supervision without requiring a separate category for every subtle difference in execution. We chose these events to translate changes in complex executions into progress relations that can be annotated reliably and used for learning.

For your example of a robot “still progressing, but slower,” we annotate events based on the actual changes in task progress during execution. If the robot moves slowly but continues to make progress without a stall or regression, no additional event annotation is needed. Such executions can receive supervision through successful trajectories. We normalize progress labels by each successful trajectory’s own completion time, so slower successful executions also provide continuous progress supervision from start to completion.

Figure R16 below shows three successful StackBowls executions that take 11.8, 29.3, and 30.9 seconds, with no annotated stalls or regressions. Although their completion times differ, all three continue to make progress. The longer executions do not contain progress stalls and therefore do not require additional stall annotations. For comparison, Figure R17 below shows two executions with stall segments during which the robot temporarily makes no further progress. The synchronized videos and prediction curves show the model’s responses during these executions.

For your example of an execution being “more easy to make mistakes,” consider a robot holding a cup with an insecure grasp while still moving it toward the target. The task is still progressing, so we would not annotate this segment as a stall or regression solely because the cup might fall. If the cup subsequently falls and causes a loss of progress already achieved, the corresponding regression event can be annotated. Our supervision focuses on progress changes that actually occur during execution. The current method has no dedicated supervision objective for grasp stability or the risk of subsequent failure.

Response · Reviewer 3ufq · Question 5

How does a progress stall differ from an unrecovered regression?

Reviewer’s original text
In Table 4, what’s the difference between Progress stall and Unrecovered regression?

Response

During a progress stall, the task temporarily makes no further progress, while progress already achieved is retained. An unrecovered regression involves a loss of progress already achieved that is not recovered during the subsequent execution. Consider a robot picking up an object to place it in a container. If the robot repeatedly attempts to grasp the object while it remains on the table, this interval is a progress stall. If the object has already been lifted but then falls back onto the table and is not picked up again before the recording ends, this is an unrecovered regression. The simulation and real-robot video comparisons (Figure R18 below and Figure R19 below) illustrate these situations, with the corresponding intervals marked on the timelines.

This distinction is also reflected in the supervision relations. During a stall, task progress within the annotated interval remains approximately equal to that of the reference state a, so we use pt ≈ pa for supervision. For an unrecovered regression, the reference state a precedes the loss of progress, and the post-loss states have lower progress, so we use pt < pa for supervision. The robot may continue trying after the regression, but if the lost progress is not restored, the regression remains unrecovered. These annotations apply to temporal intervals, and a single trajectory may contain multiple event types. We have rewritten §3.2 of the revised manuscript to make this distinction explicit. It now describes each event type separately with its supervision relation (pt ≈ pa for a progress stall and pt < pa for an unrecovered regression), and Figure 2 illustrates both with real-robot examples.
